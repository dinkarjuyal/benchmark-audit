## What's being claimed

ColBench's backend-programming track grades a submission by running it against 10 held-out unit tests and reporting the fraction that pass. This fractional score is used both to report leaderboard success rates and — since ColBench is the training environment for SWEET-RL — as the reward signal during RL training itself.

## What we found

The actual, live grading path (`check_correctness()` in [`sweet_rl/utils/code_utils.py`](https://github.com/facebookresearch/sweet_rl/blob/main/sweet_rl/utils/code_utils.py), called by `code_evaluate()`, which is the only thing `scripts/evaluate_code.py` does) decides a test case is correct with:

```python
if ground_truth_output == test_output and ground_truth_output is not None:
    num_correct += 1
```

The `and ground_truth_output is not None` clause means: whenever the *correct* answer for a test case is `None` — an entirely ordinary Python return value for "not found," an early exit, or no match — **no submission, however correct, can ever be credited for that test case.** Not even the ground-truth function itself, copied verbatim.

This was run, not just read: the comparison logic above was copied verbatim into a standalone script and executed against a ground-truth function identical to the submitted answer. Result: 0.5, not 1.0, for a submission that is correct on every test case.

**Scope:** a static search over the real eval set (`facebook/collaborative_agent_bench/backend_tasks/test.jsonl`, 10,000 tasks) for ground-truth source containing the literal string `"return None"` found **31/10,000 tasks (0.31%)**. This is a hard floor, not the true rate — it misses implicit `None` returns (falling off the end of a function body, a variable that holds `None`, etc.), so the real affected fraction is higher.

## Why it matters

This doesn't touch the raw arithmetic behind SWEET-RL's headline comparison (see the project's [statistical-validity pass](/taxonomy#statistical-validity) on this same benchmark) — every method being compared is scored by the same grader, so the bias is shared across the comparison, not a thumb on the scale for one method over another. But it's a real, structural false negative, not just an eval-reporting quirk: because ColBench's score is also the RL reward signal in SWEET-RL, every affected task silently caps the achievable training reward below 1.0 regardless of policy quality, for as long as the policy is actually correct on the None-output cases specifically.

## What would fix it

Drop the `and ground_truth_output is not None` clause, or replace it with an explicit sentinel comparison that distinguishes "test case errored" (where skipping makes sense) from "test case's correct answer happens to be None" (where it should score normally). A one-line fix in `check_correctness()`.
